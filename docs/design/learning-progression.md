## 1. 目的

プレイヤーが**化学の知識ゼロで始められ、ゲームを進めるにつれてプレイヤー自身の化学の知識が増えていく**ことを、本作の中核体験として設計する。

主人公は知識を持つ化学者だが、プレイヤーは知識を持たない。この乖離を「キャラクターの知識をプレイヤーが追体験して獲得する」構造に変換するのが本設計の狙いである。

## 2. 設計原則

| # | 原則 | 内容 |
|---|------|------|
| P1 | 新概念は1エピソードに1つ | 認知負荷を抑える。新しい概念は、その回の依頼を解くのに必要なものだけを導入する |
| P2 | 見せてから名付ける | まず現象を観察・体験させ、その後に作中表現→化学名の順で言葉を与える。専門用語の先行開示をしない |
| P3 | 失敗は教材 | 序盤の失敗は低コスト・可逆に設計し、結果には必ず「なぜそうなったか」の平易な解説を付ける |
| P4 | ヒントは学んだものだけ | ラボで参照できる助言は、知識ノートに獲得済みの概念の範囲に限る。未学習の答えをヒントで先出ししない |
| P5 | 間隔反復 | 過去エピソードの概念は、後のエピソードで文脈を変えて再利用する（例: Ep.1 の錆の知識を Ep.3 の鉛管腐食で使う） |
| P6 | プレイヤーが考える | 化学者は答えを語る役ではなく、問いを投げる役。分析と判断の主体はプレイヤーに置く |

## 3. 現状の課題（2026-11-13 時点の診断）

| 課題 | 具体例 | 違反する原則 |
|------|--------|-------------|
| 会話が結論を先に喋る | EP01 序盤で Fe₃O₄ / FeCl₂ / 塩化物錆が登場し、化学者が分析結果を narrate する。プレイヤーは観客になる | P2, P6 |
| ラボが最初から全解放 | 試薬・濃度・温度・手順・反応・濾過（＋量）が Ep.1 から全て選択可能で、重要な変数の見分けがつかない | P1 |
| 失敗から学べない | 結果表示は物語テキストのみで、失敗原因（酸の選択か、濃度か、温度か）が分解されない | P3 |
| 知識が永続化されない | 学んだ概念を保持する仕組みがなく、ゲーム側も「プレイヤーが何を知っているか」を前提に設計できない | P4, P5 |

なお土台は既に存在する。設定書 §5「世界観の化学ルール」の概念→作中表現の対応表、`treatmentEngine.ts` のパラメータ解放順（`PARAM_ORDER`）、EP01 仕様書の「分析タグ」設計（未実装）がそれであり、本設計はこれらをゲームプレイに接続するものである。

## 4. 学習ループ

各エピソードの基本ループを次の5ステップに統一する。

```
観察 → 予想 → 実験 → 解説 → ノート獲得
```

| ステップ | プレイヤーの行為 | 対応フェーズ | 実装先（現行構成） |
|----------|------------------|--------------|--------------------|
| 観察 | 依頼品・依頼人を調べ、着目点（分析タグ）を集める | フェーズ1: 対話 | DialogueScene / dialogueEngine |
| 予想 | 処方の前に「どうなるか」を選ぶ | フェーズ2 冒頭 | LabSceneVA11（新規） |
| 実験 | パラメータを選んで処置を実行（まず練習処置で試せる） | フェーズ2: ラボ | LabSceneVA11 / treatmentEngine |
| 解説 | 結果と予想を比べ、「なぜ」を平易に理解する | フェーズ3: 結果 | ResultScene / fateEngine |
| ノート獲得 | 学んだ概念が知識ノートに登録され、以後ヒント・表記に反映される | フェーズ3 末尾 | GameState（新規） |

## 5. システム設計

### 5.1 知識ノート（Field Notes）

プレイヤーが獲得した化学概念の蓄積。主人公の手帳という体裁で、ゲーム内いつでも参照できる。

**データモデル（案）**

```ts
type KnowledgeNote = {
  id: string            // 例: 'rust', 'black-rust', 'acid-strength'
  worldTerm: string     // 作中表現（先に表示される）: '錆'
  plainText: string     // 平易な説明: '金属が空気と水に食われた跡'
  chemTerm?: string     // 化学名（獲得演出後に併記）: '酸化鉄'
  chemText?: string     // 化学的な補足: '鉄が酸素と結びついたもの'
  learnedAt: string     // 獲得エピソード: 'ep01'
  relatedNotes: string[]
}
```

**運用ルール**

- 獲得前: その概念は作中表現でのみ言及され、化学名は出てこない
- 獲得の瞬間: 結果フェーズで「新しい知識を得た」演出と共に、作中表現→化学名の二段表記が開示される
  - 例: 「黒錆 — 化学では Fe₃O₄（四酸化三鉄）と書く」
- 獲得後: 会話・ラボ・結果テキストで化学名が併記されるようになる
- ラボのヒント表示は獲得済みノートの内容だけから構成する（原則 P4）

**EP01 で獲得するノート（案）**

| id | 作中表現 | 平易な説明 | 化学名 | 獲得タイミング |
|----|----------|------------|--------|----------------|
| rust | 錆 | 金属が空気と水に食われた跡 | 酸化（腐食） | 観察で剣を見た時 |
| black-rust | 黒錆 | 表面を覆う黒い錆の層 | Fe₃O₄ | 練習処置で黒い液の変化を見た時 |
| chloride-rust | 白っぽい錆 | 海の塩が運んだ、白灰色の錆。普通の錆より性質が悪い | 塩化物錆（FeCl₂ 系） | 観察で出自（港町）を聞いた時 |
| acid-strength | 酸の強さ | 酸には「よく溶かすが荒いもの」と「穏やかなもの」がある | 酸の種類と性質 | 試薬を選ぶ時 |
| concentration | 濃さの加減 | 濃いほど強力だが、相手まで傷める | 濃度 | 濃度パラメータ解放時 |
| heat-risk | 熱の危うさ | 熱は反応を速めるが、暴走と副産物も招く | 温度依存性・副反応 | 温度パラメータ解放時、または過熱を経験した時 |

### 5.2 パラメータの段階解放

`treatmentEngine.ts` の `PARAM_ORDER`（acid → concentration → temperature → procedure → reaction → filtration）を、エピソード内・エピソード間の解放スケジュールとして正式に採用する。

- 解放されていないパラメータは、UI 上は「まだ扱えない」ことが分かる見た目で、既定値（安全な標準値）が入っている
- 解放は対応するノートの獲得と同時に行う（学んだから扱える、という因果を付ける）
- 量（Qty）の選択肢は、当面は照合スコア専用の補助パラメータとし、解放対象には含めない

**解放スケジュール（案）**

| 時期 | 解放 | 紐づくノート |
|------|------|--------------|
| EP01 開始時 | 試薬（種類のみ） | acid-strength |
| EP01 練習処置の後 | 濃度 | concentration |
| EP01 本番前 | 温度 | heat-risk |
| EP02 | 手順（時間）＋ pH の概念 | （Ep.2 のノート） |
| EP03 | 反応・濾過 | （Ep.3 のノート） |
| EP05 以降 | 純度・触媒系（purityEngine 側） | （Ep.5 のノート） |

### 5.3 予想フェーズ

処置の実行前に、プレイヤーに結果の予想を選ばせる。

- 選択肢は結果カテゴリに対応する3〜4択（例: 「錆だけが落ちて、刃は無事だと思う」「錆は落ちるが刃も傷みそう」「ほとんど落ちないと思う」「何か危ないことが起きそう」）
- 予想は知識ゼロでも選べる粒度にし、正解を暗記させるのではなく「自分の仮説を持つ」こと自体を目的とする
- 結果フェーズでは予想と結果を並べて表示し、一致・不一致に応じた化学者の一言（解説）を出す
- 予想的中には小ボーナス（観察眼ポイント等、数値設計は未決事項 §8）。外れても罰はなく、解説が詳しくなるだけにする

### 5.4 練習処置（テストピース）

本番の対象に触る前に、代替素材で同じ処方を試せる仕組み。実際の化学実験におけるスポットテスト／テストピースに相当する。

- EP01 ではガルドの工房にある錆びた端材（剣と同じ系統の錆を持つ鉄片）を使う
- 練習では事故・致命的な失敗が起きず、結果の数値（除去率・侵食・副産物の有無）だけが簡易表示される
- 回数は無制限（または低コスト）とする。練習結果を見て処方を直し、本番に臨む流れを基本形にする
- 練習で初めて見る現象（液の変色、泡立ち等）がノート獲得のトリガーになる（原則 P2）

### 5.5 解説フィードバック

結果フェーズのテキストを「物語」と「分析メモ」の2層にする。

- 物語層: 現行の fateEngine の結果テキスト（依頼人の反応・結末）
- 分析メモ層: 失敗・成功の要因分解を平易に表示する。生成は機械的に行う
  - 酸の選択: `MatchDetail.acid` と対象の腐食種別から（例: 「塩酸は塩化物錆を悪化させる。酸の選択が原因」）
  - 濃度・温度: reactionEngine の内訳（除去率・侵食率・超過分）から（例: 「温度が高すぎて金属まで攻撃した」）
  - 副産物: byproductHazard から（例: 「塩酸を濃く熱したため、刺激性の気体が出た」）
- 分析メモで触れる概念は、獲得済みノートの表現を優先し、未獲得の概念はここで新規獲得に繋げる

### 5.6 会話設計（分析タグの実装）

EP01 仕様書にある分岐会話＋分析タグの設計を実装し、対話フェーズを「観察」の場にする。

- プレイヤーの選択（何を観察するか、何を聞くか）で分析タグが付く
- タグの組み合わせから「分かりかけていること」がノート形式で提示される（答えではなく、観察事実の整理）
- 化学者の台詞は結論の narrate をやめ、問いかけと観察の促しに寄せる
  - 例（現行）: 「表面の腐食は二層になっている。上層に黒い酸化物——Fe₃O₄……」
  - 例（変更後）: 「よく見てくれ。錆の色が、場所で違わないか？」→ プレイヤーが着目点を選ぶ → タグ獲得

## 7. EP01 リデザイン仕様（要約）

現行 EP01 への変更点のみを挙げる。勝敗の数値仕様（最適条件・結末表）は変更しない。

1. **観察パート化**: 線形会話を、EP01 仕様書の分析タグ分岐に置き換える。タグ3種（黒錆／塩化物錆／出自）を集めると観察完了
2. **ノート獲得**: 観察と練習の過程で §5.1 のノート6種を順に獲得する
3. **練習処置の追加**: 本番前に端材で1回以上の試行を挟む。練習でのみ、リン酸・塩酸それぞれの反応の違いを安全に観察できる
4. **解放の適用**: ラボは試薬のみで開始し、濃度→温度の順に解放する
5. **予想の追加**: 本番実行直前に予想を1つ選ばせる
6. **結果の2層化**: 結末テキストに分析メモを追加し、予想との照合コメントを出す
