# [ADR-0001] Clean Architecture パターンの採用

* **ステータス**: 承認 (Accepted)
* **決定者**: Project: FLASK アーキテクチャチーム
* **日付**: 2026-10-06
* **関連要求**: 全要求 (`REQ-CHEM-*`, `REQ-FATE-*`, `REQ-ATOM-*`, `REQ-LAB-*`, `REQ-TALK-*`)

---

## 1. 文脈と問題提起 (Context & Problem Statement)

『Project: FLASK』は、物理化学シミュレーション（原子の結合、温度・触媒による純度計算）とアドベンチャーゲームの会話・運命分岐システムを融合させたシステムである。
今後、Web API（Flask）としての提供だけでなく、CLI、単体テストランナー、さらにはスタンドアロンなゲームクライアント（GodotやUnity等）へのエンジン組み込みや、ストレージ（SQLite、インメモリ、PostgreSQL）の換装が想定される。

従来の密結合な Flask アプリケーション構成（Route 内にビジネスロジックや DB 操作が混在する構造）を採用した場合、以下の問題が生じる。
1. フレームワーク依存により単体テストが鈍化し、Fast Tests（数秒での実行）が困難になる。
2. ドメインの物理化学計算ロジックに Web や DB の詳細が漏洩し、保守性と決定論的検証が阻害される。
3. 将来的なフロントエンドやインフラの切り替え時に、全コードの大規模改修が発生する。

---

## 2. 検討した選択肢 (Considered Options)

* **選択肢 A: 伝統的な Flask MVC / Active Record パターン**
  - Flask の標準的な Blueprint + SQLAlchemy モデルにロジックを直書きする構成。
  - *メリット*: 初期実装速度が速く、ボイラープレートが少ない。
  - *デメリット*: ドメインロジックが Flask/DB に密結合し、テストに DB モックやクライアントコンテキストが必須となる。アーキテクチャの侵食を防げない。
* **選択肢 B: Clean Architecture (Hexagonal / Ports and Adapters)**
  - システムを Domain, Use Cases, Adapters, Infrastructure の 4 層に分離し、依存性を内側（Domain）へ一方向に限定する。
  - *メリット*: ドメイン層が外部ライブラリから完全隔離され、ピュア Python による超高速な単体テストが可能。ビジネスロジックの再利用性と長期保守性が最大化される。
  - *デメリット*: インターフェース定義や DTO 変換などのファイル数・初期ボイラープレートが増加する。

---

## 3. 決定と根拠 (Decision Outcome & Rationale)

**選択肢 B（Clean Architecture）を採用する。**

### 主たる理由
1. **ドメインロジックの保護**:
   - 原子の結合ルールや純度計算式、因果分岐判定は本プロジェクトの中核資産であり、Flask や DB の都合から完全に独立していなければならない。
2. **高速・決定論的なテストの実現**:
   - `src/domain/` は純粋な Python 標準ライブラリのみで書かれるため、DB や HTTP コンテキストの起動を伴わずミリ秒単位で数千件のテストを実行できる（テストピラミッドの基底70%を強固に支える）。
3. **Fitness Functions による自動ガバナンス**:
   - 依存方向のルールを `import-linter` で CI 自動検査できるため、複数人開発や AI エージェント開発においても構造の腐敗を機械的に防止できる。

---

## 4. 評価と結果 (Consequences)

### 正の影響 (Positive Consequences)
* ドメインロジックが 100% 独立し、フレームワークのバージョンアップや変更の影響を受けない。
* ドメイン層のブランチカバレッジ 95% 以上を容易に維持可能。
* ビジネス要求（`REQ-xxx`）とドメインエンティティ・ユースケースの 1 対 1 トレーサビリティが明確になる。

### 負の影響 / リスク (Negative Consequences / Risks)
* レイヤー間の DTO / エンティティ変換の手間が発生する。
* 「1ターン最大3ファイル制限」を意識した適切な粒度でのインクリメンタルな開発運用が求められる。

---

## 5. 適合度関数 / 検証基準 (Fitness Functions & Validation)

本決定の遵守は、CI パイプライン上の以下の自動テストで検証する。
1. **`import-linter` 契約検査**:
   - `src/domain/` が `flask`, `sqlalchemy`, `src.adapters`, `src.infrastructure` をインポートしていないことを機械的に検証（違反時は CI 即時 Fail）。
2. **レイヤー別カバレッジ検査**:
   - `src/domain/` のブランチカバレッジ $\ge 95\%$ を強制する。
